# 派工 Prompt 模板

用法：選對任務型態 → 複製模板 → 填掉所有 `【】` 空格 → 用 Agent 工具發出。**`【】` 一個都不能留空**；填不出「驗收條件」代表你自己還不清楚要什麼，先想清楚再派。

每個模板標了建議的 `subagent_type` 與 `model`，照 [model-dispatch.md](model-dispatch.md) 規則五升降級。派工前自查：目標動機有了嗎？驗收條件可客觀判定嗎？回報格式限制了長度嗎？

---

## 1. 搜尋（subagent_type: `Explore`，model: `sonnet`）

```
目標：找出【要找什麼：pattern / 函式用法 / 慣例 / 所有呼叫點】。
動機：【為什麼要找，找到後要拿來做什麼——這決定你該回報到多細】。
範圍：【目錄或檔案範圍，例如 src/actions/ 與 src/lib/；沒把握就寫「全 repo，排除 node_modules/.next/docs」】。
搜尋強度:【medium／very thorough——影響它掃多廣】

驗收條件：
- 每個結果附「檔案路徑:行號」與不超過 5 行的關鍵片段。
- 明確回答「是否可能有遺漏」：列出你搜過的關鍵字與沒搜的變體。

回報格式：條列，每條一個發現。最後一段寫「結論：【一句話回答我的問題】」。
不要貼整個檔案內容。找不到就回報「未找到＋你試過的搜法」，不要猜。
```

## 2. 實作（subagent_type: `general-purpose`，model: `sonnet`；跨模組或涉及審批流/fullId cascade 用 `opus`）

```
目標：【要做出什麼行為，從使用者角度描述】。
動機：【為什麼做、誰會用——遇到規格沒寫到的岔路時，照這個動機取捨】。
先讀：CLAUDE.md 的 Domain Rules 與 Security Checklist；【其他必讀檔案，如 docs/backup-restore-design-reference.md】。
限制：【不可以動的檔案／不可以改的行為／必須沿用的既有模式，例如「Server Action 回傳 { success, error?, data? }」】。

驗收條件（全部要有證據）：
- 【功能性條件，例如：在 X 頁面做 Y 會看到 Z】
- npx tsc --noEmit 無錯誤。
- npx vitest run 全綠；【若碰 fullId：必跑 src/lib/__tests__/fullid-cascade.test.ts】。
- 新增／修改的使用者可見文字為繁體中文。
- 若碰 mutation path：逐條對照 Security Checklist 並在回報中逐條打勾。

回報格式：
1. 結論（完成／未完成＋差什麼）。
2. 改動清單：每個檔案一行，「檔案:行號區間 — 改了什麼、為什麼」。
3. 驗證證據：實際命令輸出的最後幾行，不是「我跑過了」。
4. 風險與未處理事項。
禁止回貼完整檔案。禁止「應該可以」式結論。
```

## 3. 重構（subagent_type: `general-purpose`，model: `sonnet`）

```
目標：【重構什麼、變成什麼形狀，例如「把 X 的重複邏輯抽到 src/lib/Y」】。
動機：【現在的痛點】。
行為不變是硬約束：重構前後對外行為必須完全一致。任何你認為「順便修掉的 bug」都不准修——記下來回報，讓我決定。

步驟要求：
1. 先跑 npx vitest run 記錄基線（哪些綠、哪些本來就紅）。
2. 重構。
3. 再跑一次，結果必須與基線完全相同。

驗收條件：
- 測試結果與基線一致（貼兩次輸出對照）。
- npx tsc --noEmit 無錯誤。
- 【量化目標，例如：重複的 cascade 邏輯只剩一份；X.ts 行數下降】。

回報格式：結論／改動清單（檔案:行號）／基線對照證據／發現但未修的問題清單。
```

## 4. 研究（subagent_type: `general-purpose`，model: `sonnet`）

```
問題：【要回答的具體問題，一句話】。
動機：【要用這答案做什麼決策】。
來源優先序:【例如：官方文件 > 本 repo 現況 > 部落格。查外部函式庫用 Context7 工具，查不到再 WebSearch】。

驗收條件：
- 每個關鍵結論附來源（URL 或 檔案:行號）。
- 區分「確認的事實」與「推測」，推測要標明。
- 若結論影響本 repo 的既有寫法，指出衝突點在哪個檔案。

回報格式：先一段直接回答問題，再列證據。全文不超過 40 行；
超過的細節寫到【scratchpad 路徑或 docs/ 指定檔案】，回報檔案路徑。
查不到就回報「查不到＋試過的來源」，不要編造。
```

## 5. 審查（優先用 rms-* 專屬審查員：安全→`rms-security-reviewer`、後端→`rms-backend-reviewer`、前端→`rms-frontend-reviewer`、跨層→`rms-architecture-reviewer`；不指定 model，定義檔已設定。範圍不合的一般審查用 `feature-dev:code-reviewer` + `sonnet`）

```
審查範圍：【diff 範圍，例如「git diff main 的全部改動」或指定檔案清單】。
背景：【這批改動要做什麼——審查員需要知道意圖才能判斷「做的對不對」而不只是「寫得好不好看」】。
重點維度：【例如：自我審批防護、fullId 一致性、transaction 完整性；沒有特別重點就寫「正確性優先，風格其次」】。

驗收條件：
- 每個 finding 附：嚴重度（Critical/High/Medium/Low）、檔案:行號、具體失敗情境（什麼輸入會造成什麼錯誤結果）。
- 「可能有問題」而驗證不了的，標 PLAUSIBLE，與確認項分開列。
- 沒問題就明說「未發現 X 維度的問題」，列出你檢查過什麼。

回報格式：finding 依嚴重度排序條列；最後給一句總體判斷（可合併／需修再合／需重做）。
不要求改 code，只回報。
```

## 驗收派工（附屬模板：驗證不自驗用）

實作完成後，派一個**沒看過實作過程**的驗證員。model 依驗收性質選：涉及判斷力的驗收至少與實作者同級；純機械式驗收（檔案存在、章節齊全、跑命令看輸出）用 `sonnet`（見 model-dispatch.md 規則六）：

```
你是驗收員，驗收與你無關的另一個 agent 的產出。不要幫它圓場。
待驗收物：【檔案清單或功能描述】。
驗收條件清單：【原封不動貼上派工時的驗收條件】。

對每一條回報：通過／不通過＋證據（命令輸出或 檔案:行號）。
能用命令驗的必須實際執行命令，不准用閱讀代替執行。
最後結論只能三選一：全部通過／部分通過（列出缺項）／不通過。
```
