## 1. Server Actions 模式一致性

### [High] B-1: 錯誤處理模式不一致 — throw vs return

**問題**: 7 個 action 檔案（共 72 處）使用 `throw new Error`，而 4 個檔案（共 42 處）使用 `return { success: false, error }`。

**影響**:
- `throw new Error` 會導致 Next.js 回傳 500 錯誤，client 端無法取得友善錯誤訊息
- `return { success: false, error }` 讓 client 可以顯示具體錯誤

**統計**:
| 檔案 | throw | return { success: false } |
|------|-------|---------------------------|
| approval.ts | 19 | 0 |
| data-files.ts | 33 | 0 |
| notifications.ts | 5 | 0 |
| users.ts | 5 | 0 |
| qc-approval.ts | 5 | 0 |
| item-reorder.ts | 0 | 22 |
| item-restore.ts | 0 | 13 |
| item-relations.ts | 0 | 6 |

**修復建議**: 統一所有 Server Actions 使用 `return { success: false, error }` 模式。保留 `throw` 僅用於真正的不可預期錯誤。

## 2. fullId Cascade 兩階段重命名

### 正面發現

- `collectDescendantChanges()` 在 `batchCascadeFullIdChanges()` 之前被正確呼叫
- 兩階段重命名使用 `__TEMP_` 前綴避免唯一約束衝突
- 軟刪除項目使用 `__DELETED_` 前綴處理正確
- 所有 cascade 操作在同一個 `prisma.$transaction` 中
- `item-reorder.ts` 有 4 個 transaction，覆蓋所有需要原子性的操作

### [Medium] B-2: export-service.ts 匯出未過濾 isDeleted

**位置**: `src/lib/backup/export-service.ts` L199
**問題**: `prisma.item.findMany({ where: { projectId } })` 匯出所有 items，包括 soft-deleted 的。匯入到新環境後，已刪除的 items 仍然存在。
**影響**: 非嚴重，因為匯入後 isDeleted flag 仍然保留，但可能造成資料庫膨脹。
**修復建議**: 考慮提供選項是否包含已刪除項目。

## 3. 審批 Pipeline 狀態機

### 正面發現

- ChangeRequest: PENDING → APPROVED/REJECTED 狀態轉換正確
- QCDocumentApproval: PENDING_QC → QC_APPROVED → PM_APPROVED/REJECTED 完整
- 自我審批防護: `approval.ts` L886 和 `data-files.ts` L364 正確阻擋
- 拒絕後重新提交: 通過 `previousRequestId` 鏈正確實作

### [High] B-3: batchApproveAsPM 非原子操作

**位置**: `src/actions/qc-approval.ts` L316-347
**問題**: `batchApproveAsPM` 使用 `for...of` 迴圈逐一處理每個 approval，不在 transaction 中。如果處理到一半失敗，部分已核准、部分未核准，造成不一致狀態。
**修復建議**: 使用 `prisma.$transaction` 包裹整個迴圈，或明確文檔化 partial success 是預期行為（目前返回 `{ successful, failed }` 結構暗示這是預期的）。

## 4. Prisma 查詢品質

### [Medium] B-4: 部分 findMany 查詢缺少 take 限制

**位置**: 多處
**問題**: `data-files.ts` L54 的 `getDataFiles()` 和 `search.ts` L56 的 `searchProjectItems()` 未設定 `take` 限制，大量資料時可能導致記憶體問題。
**修復建議**: 加入分頁或合理的 `take` 上限。

### [Medium] B-5: revalidatePath 路徑不一致

**問題**: 審查發現 revalidatePath 的使用模式不統一：
- `approval.ts`: 混用 `/admin/approval` 和 `/admin/approvals`（拼寫不一致）
- `data-files.ts`: revalidate `/admin/approval` 和 `/datafiles/${fileId}` 但不 revalidate list 頁
- 部分 action 缺少對 layout 的 revalidate

**修復建議**: 建立 revalidation helper，確保所有相關路徑都被正確 invalidate。

## 5. Backup/Restore

### 正面發現

- Database restore 在 `prisma.$transaction` 中執行
- FK constraints 先 drop 後 recreate
- PostgreSQL sequence 重置到 `MAX(id) + 1`
- SQL 白名單驗證正確
- Zip Slip 防護完整

### [Medium] B-6: project import 中 ID mapping 可能不完整

**位置**: `src/lib/backup/import-service.ts`
**問題**: 匯入時會建立 ID mapping（舊ID → 新ID），但若 manifest 中引用的關聯 ID 不存在於 mapping 中，可能靜默失敗。
**修復建議**: 加入 mapping 完整性檢查和警告日誌。
